# HETA F1 recovery — Block B: standalone signature validation

**Date:** 2026-10-20. **Main baseline:** `c23d74da88042ef18cbb3964f0c2b65423994591`.
**Candidate inspected:** `ccr-heta01-f1-impl1` at `86f709d62891a396fa040c14783faae6526e8a5c`.
**Scope:** selectively incorporate and harden only the candidate signature helper, with synthetic tests. No production caller, barrel export, route, capture repository or deployment wiring is introduced.

## Source and requirement boundaries

HETA-01B requires authenticated raw-body verification before trusting provider evidence and excludes signature validity as independent historical-tier authority. The existing webhook already uses the installed Stripe SDK and WebCrypto provider. This block preserves that deployed route and SDK version; it reviews the candidate helper against the installed SDK's `Webhooks.js`, rather than inventing an independent HMAC implementation for the application.

Revision 3.3 and H1–H20 remain unavailable. The SHA-256 reported in PR #140 is not verified against original bytes. The candidate's envelope, keyring and shape modules were inspected, but their persistence format, AAD, cohort/runway, custody, retention, attribution and quarantine contracts are not adopted by this block. No candidate catalog/schema/test bundle is imported. PR #142 remains the separate source-gap reconciliation draft; merged Block A remains storage characterization, not full acceptance.

## Reproduced defects and narrow corrections

The first run of 32 new synthetic tests against the unmodified candidate helper produced **12 failing assertions and 20 passing assertions**. These include strictness/diagnostic expectations as well as confirmed verification/provenance defects; the count is not twelve independent vulnerabilities.

| Finding                           | Reproduction                                                                                                                                                                                                                                                                              | Correction                                                                                                                                                                                                               |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Header parser disagreement        | The helper trims or ignores malformed timestamp fields while the installed SDK parses untrimmed fields and uses `parseInt`. A signed synthetic future timestamp with a malformed suffix or a duplicate whitespace-prefixed field can pass while the helper records a different timestamp. | Require exactly one valid timestamp, reject malformed recognized timestamp/signature fields and whitespace ambiguity, then pass the unchanged raw header/body to the SDK. Multiple valid v1 signatures remain supported. |
| Freshness bypass through options  | Zero, negative, NaN or infinite tolerance disables/bypasses SDK age enforcement. Invalid Date also produces an ineffective comparison.                                                                                                                                                    | Reject non-finite/non-positive tolerance and invalid clocks. Enforce a finite symmetric freshness window. Keep default 300 seconds and valid positive overrides.                                                         |
| Mutable provenance instant        | The returned `verifiedAt` aliases the caller's Date; changing that Date changes the prior result.                                                                                                                                                                                         | Snapshot verification time before awaiting cryptographic verification.                                                                                                                                                   |
| Missing configuration diagnostics | Empty secret configuration already fails in the installed SDK, but returns a generic invalid-signature reason; an empty label could appear in provenance.                                                                                                                                 | Fail closed with existing `NO_SECRET` for missing secret/label configuration. No secret format, custody, rotation schedule or new policy is prescribed.                                                                  |
| Crypto-provider initialization    | Candidate provider-operation exceptions are caught, but provider construction occurs outside that boundary.                                                                                                                                                                               | Return existing redacted `INVALID_SIGNATURE` on initialization failure, without exposing provider exception text.                                                                                                        |

All public type/field names and result variants are retained. Behavior is intentionally stricter than the unmerged candidate for ambiguous headers, disabled freshness and missing configuration. This helper is intended for fresh receipt verification, not an offline replay mode. That tightening is not silently applied to the existing webhook or candidate branch. Any future integration must reconcile its calling contract and separately approve acknowledgement/capture behavior.

Synthetic fixtures require knowledge of their synthetic HMAC input. They demonstrate validation behavior, not an ability to forge Stripe signatures without the signing secret. The tests use Node HMAC to construct independent fixtures; application verification continues through the existing Stripe SDK and WebCrypto implementation.

## Verification scope

The final focused suite contains **35 tests** for exact-byte authentication, current/previous secret selection, multiple v1 signatures, signed non-JSON bodies, altered bodies, wrong secrets, stale/future timestamps, inclusive window boundaries, missing/malformed/ambiguous headers, unsafe tolerance/clock values, missing configuration, caller-Date mutation, provider initialization/operation failure redaction and absence of network requests.

No raw provider event is parsed, attributed, persisted or treated as effective-time evidence by the helper. Successful output is signature provenance only. Failure returns stable result codes; no body/header/secret or SDK exception text is logged or returned. Production import search finds no caller outside the helper's tests. Local API source/test typechecks, focused lint, formatting and diff checks passed. All **701 API unit tests in 59 files** passed, including the 35 new cases. CI results are recorded against the exact PR SHA before review.

These are standalone signature tests, not AES-GCM/envelope tests, key-custody certification, provider configuration tests, PostgreSQL concurrency/isolation tests, or original T01–T44 acceptance. Existing CI's PostgreSQL/storage/Block A checks run separately and do not close missing design or HETA-01G gates. No new local database is needed for this pure helper.

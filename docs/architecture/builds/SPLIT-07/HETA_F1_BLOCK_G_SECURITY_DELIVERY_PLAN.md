# HETA-01-F1-G — Proposed delivery, database security and implementation gates

**PROPOSED; documentation only.** See [decision register](HETA_F1_BLOCK_G_DECISION_REGISTER.md) and [identity/attestation contract](HETA_F1_BLOCK_G_IDENTITY_ATTESTATION_CONTRACT.md). Nothing here changes an existing HTTP response, role, migration, setting or financial guard. Implementation and staging/production authorization are not granted.

## Durable receipt transaction — G5

Future pipeline: bounded raw-body acquisition -> exact-byte signature verification -> envelope/context classification -> encryption using approved key custody -> short database receipt transaction -> committed response -> independent reconciliation. Current route still verifies then synchronously processes the legacy mirror and limited 0043 observations; this design is a separately approved cutover, not a claim about deployed behavior. Proposed fast acknowledgement follows durable preservation, not completion of business projection. It is consistent with HETA-01B's no-false-capture-ack boundary; Stripe's [webhook guidance](https://docs.stripe.com/webhooks) supports short responses and asynchronous work.

**Before transaction:** bound input/memory/time, snapshot verification clock and trusted endpoint/config revision, authenticate exact bytes, classify supported envelope, encrypt body and compute its raw digest. Do not perform provider network calls while holding database locks. Key initialization/custody and retention remain separate unresolved approvals; Blocks C/E do not approve a production keyring. Missing account attestation does not invent a canonical key or successful attestation reference.

**Within one transaction:** revalidate current context/attestation/incident revision if linking; acquire deterministic logical-key or unresolved-observer lock; resolve full tuple uniqueness; persist encrypted original/observation and delivery record; append restricted quarantine/conflict disposition where required; persist one durable reconciliation work marker keyed by approved logical operation/revision. Conflict variants are not discarded by a blind ON CONFLICT DO NOTHING. Atomically persist conflict hold before a competing worker can consume the old state. Unresolved observations use separately designed restricted storage, not a fake mandatory 0045 FK.

Record observation identity independently of logical event identity. Exact representation reuse requires matching provider tuple, acquisition scope, provenance and byte digest, with a separately retained delivery context. A different endpoint, method, attestation or signature label must not have its provenance silently dropped; it can append its own observation/delivery. Stable idempotency/work keys exclude ephemeral signature timestamps and API request IDs. Event IDs alone and caller-supplied business claims are not sufficient keys. Future schema must express these constraints, not rely on helper-only tests.

**After commit:** return the proposed response. A worker claims committed work using explicit leases/attempts and lock ordering, appends results, and rechecks context/conflict/binding revisions at commit. Crash recovery uses the durable marker, not a best-effort queue send. Projection and 0043 coexistence require reviewed ordering/idempotency and replay rules before any cutover. No new financial consumer is included. A provider webhook ack only means receipt safely preserved under this contract.

Response codes are explicit owner proposals, not live behavior. 200 for a conflict or malformed payload acknowledges safe restricted preservation only. Unknown commit outcome must return failure unless durability is positively confirmed. No alert can substitute for missing durable quarantine. Unsupported synchronous authorization/event products are excluded from this asynchronous subscription-evidence contract.

Recommended observability: counts/latencies for verified/unresolved/duplicate/conflicted/retrieval failure, oldest work age, scope revision drift, key outage and coverage gaps. Alerts include opaque evidence/config/incident IDs and redacted codes, never raw payloads, signature values, API credentials, private cross-business identifiers or misleading “tier verified” labels. Outage closure requires a bounded retrieval/replay manifest and explicit unresolved gaps; no empty list or successful retry certifies history. Operator remediation is least-privilege, audited and append-only.

## Least-privilege database plan — G6

**Observed:** `createDb` uses the configured Hyperdrive connection string. Source does not prove which production role it represents. F's owner/superuser/BYPASSRLS observations describe its disposable database only. Current six evidence tables have append-only triggers and no RLS in that tested baseline. Existing application tenant middleware verifies membership, branch and permissions; it does not establish evidence-table database isolation. No live role, password, grants, RLS, Hyperdrive binding or staging/production SQL is accessed in Block G.

Recommend separate credentials/connections and narrow operations, not an owner role shared by all services:

| Proposed principal                                                                      | Required access                                                                                                                      | Explicit denial                                                                                             |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Offline migration owner (nonlogin owner plus separately controlled migration principal) | Reviewed additive DDL and audited grant installation in separately authorized maintenance                                            | No ordinary application login/automatic deployment migration path                                           |
| Receipt writer                                                                          | Approved insert-only receipt operation; narrowly scoped idempotency lookup/result; required sequences only                           | No assertion mint/revoke, raw global SELECT, update/delete/truncate, DDL, role switching or economic access |
| Verification service                                                                    | Protected append operation for assertion/lifecycle records after independent principal/method verification                           | Capture writer cannot impersonate it; no economic mutation or raw tenant history browsing                   |
| Reconciler                                                                              | Scoped encrypted observation read, approved key-service unwrap, verified binding read, append dispositions and lease/work operations | No rewriting originals, granting tenant ownership from metadata, broad billing/economic writes              |
| Tenant projection reader                                                                | Only approved minimal projection after independent verified business binding and current app membership/branch/permission checks     | No raw events, quarantine, credentials, other businesses, unrestricted evidence enumeration                 |
| Forensic/audit reader                                                                   | Time-limited explicitly approved incident scope and export audit                                                                     | No ordinary tenant exposure, assertion minting, rewrite or silent export                                    |

All runtime roles: nonowner, nonsuperuser, no BYPASSRLS, no membership in owner roles, no CREATE/ALTER/TRUNCATE/trigger administration, minimal sequence/schema grants, no economic table writes. Append-only triggers protect ordinary operations, not malicious administrators. Separate service identity is essential: a freely supplied actor column is not authenticated authority. Request-scoped authorization and evidence access logs bind workload identity, rule revision, scope and correlation ID; audit retention/export access is separately approved.

**RLS recommendation:** use service grants for pre-tenant evidence, with no raw tenant access. Only verified bound projections expose tenant data; implement default-deny RLS on those future structures as defense in depth, enforce ownership separation and consider FORCE RLS for owner mistakes. Superuser/BYPASSRLS remain outside that protection ([PostgreSQL documentation](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). Do not add a business_id chosen by capture to “solve” quarantine visibility.

**Trusted context requirement:** a shared role accepting `SET app.business_id` from arbitrary SQL cannot authenticate tenancy. Prefer a protected authorization broker/operation boundary that validates server-authenticated membership and establishes transaction-bound scope not forgeable by the tenant-facing role. Tenant reader gets only audited scoped operations, not global table SELECT or a bypassing function; if this cannot be enforced, choose separately scoped database principals instead. Concrete mechanism, function grants/search_path and identity proof must be approved and adversarially tested before implementation. A compromised broker/shared privileged reconciler remains a blast-radius risk, not solved by RLS; isolate it and audit every privileged read. No direct client SQL access.

Hyperdrive/pooling plan must demonstrate BEGIN -> trusted context establishment -> scoped operation -> COMMIT/ROLLBACK; no session-level context assumptions, leaked role switching, reused tenant identity or reliance on an unknown pooled backend. Empty/invalid context defaults to deny. If a SECURITY DEFINER operation is necessary, specify a non-superuser owner, fixed search_path, qualified objects, revoked PUBLIC execute, parameter validation, bounded scope and deny arbitrary SQL; independent review is mandatory. No function in this package is executable SQL.

### Migration readiness and compatibility

**NOT READY for production migration.** G1–G6 choices, original-source reconciliation, key custody/retention, actual-role inventory and acceptance evidence are unresolved. Journal currently ends at 0045; allocate a new migration number only against then-current main. No SQL is generated or edited here.

Future separate proposal must: preserve 0040–0045 bytes/hashes; add observer/logical-link/assertion/lifecycle/work/projection structures and constraints; model malformed multi-context observations without global digest suppression; define nullable unresolved linkage without fake passed rows; preserve old UUID/FK references and original provenance; include indexes, append-only protection, ownership/grants and default-deny visibility. Legacy mapping remains explicitly unresolved until independently verified. No event-ID-only merge, schema-inferred attestation or fabricated 0043 envelope backfill.

Prove clean install and prior-schema upgrade with synthetic collisions/unresolved data, idempotent replay, no lost observations, deterministic lock ordering, and zero effect on subscription mirror/auth flows or economic denials. Install roles/grants separately under owner approval before any connection cutover. Rehearse revoke/cutover/rollback on disposable databases; rollback stops new consumers/writers and uses a reviewed forward repair, never drops evidence or disables guards. Actual Hyperdrive connection replacement requires its own authorization, verified role inventory and staging evidence.

# HETA-01-F1-G — Proposed identity and attestation contract

**PROPOSED; not implemented or approved.** Baseline and authority: [G decision register](HETA_F1_BLOCK_G_DECISION_REGISTER.md). G1–G4 below are new proposal identifiers, not H1–H20 recovery. S1–S5 refer to the register's official source links. Normative language in this file describes the proposed future system only.

## Canonical identity and trust boundaries — G1

Represent keys as typed tuples with explicit field types and a versioned, unambiguous encoding; never concatenate arbitrary delimiters or derive a key from payload SHA-256. Any hash used as an index must retain and compare the full tuple; collision handling cannot merge unrelated events.

| Proposed field     | Meaning and trusted source                                                                                                                   | Untrusted/forbidden substitute                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| provider_namespace | Registry value `stripe:v1:snapshot`; other formats require separate contract                                                                 | Caller-selected provider/format; thin/v2/context auto-coercion                                |
| provider_realm     | Stable registry ID for independently verified provider isolation realm (including sandbox where applicable); not local dev/staging/prod name | Secret prefix, hostname or asserted realm without attested inventory                          |
| origin_account_id  | Direct: attested receiver account. Connect v1 snapshot: authenticated event.account consistent with verified relationship and API context    | Metadata, request header chosen by public caller, account found inside data.object alone      |
| livemode           | Authenticated event claim checked against attested allowed operating scope and retrieval context                                             | Production URL implying live; API secret naming alone                                         |
| provider_event_id  | Validated snapshot Event ID in authenticated envelope or trusted Event retrieval response                                                    | Customer/object ID, fabricated surrogate, current subscription response masquerading as Event |

Logical uniqueness is exactly this tuple. Stable `logical_event_id` UUID is its internal reference. Receiver, endpoint ID, signing label, provenance, signature timestamp, raw digest, API rendering version, receipt time and local business ID are excluded from logical uniqueness. Receivers in the same verified realm may attach observations to one logical event only after each relationship is validated. If two local deployments share that realm, deployment IDs must not split the provider identity. Unknown realm/account/scope means no canonical key, not a default receiver guessed from metadata. Identical event-ID strings in different realms/accounts/modes remain distinct.

The supported set is deliberately limited to reviewed v1 snapshot direct/Connect events. Thin events, organization contexts, v2 origin rules, unusual account equality or unknown renderers stay restricted/unresolved until separately reviewed. S1/S2 show context-sensitive event/account fields; they do not justify universal coercion.

Proposed immutable layers:

1. **Acquisition observation:** independent UUID; original encrypted representation/digest, received/retrieved and committed timestamps, acquisition type, trusted receiver/endpoint/config revision, signature verification OR retrieval evidence, API version, attestation reference and rule version. A verified signature authenticates bytes, not deployment configuration. Never store secret values in provenance.
2. **Logical event:** scoped tuple plus UUID; no tenant/economic ownership. Creating a link requires G3 and an immutable decision; unresolved observations retain their UUID without a fabricated logical ID.
3. **Delivery receipt:** observation reference plus endpoint/attempt metadata and independent signature verification where available. Exact replay may reuse the stored representation while appending delivery evidence. It must not create a new logical event or semantic authority.
4. **Reconciliation/disposition:** append-only observation links, comparison rule/version, compared fields, reason codes, conflict references, decision actor and revision. Changes are new decisions, not edits to originals.
5. **Business binding:** separately verified account/mode/customer/subscription/business lifecycle proof and binding revision, under HETA-01B. Neither canonical key nor signed metadata creates tenancy. Subscription replacement cannot overwrite prior binding history; branches inherit the verified business, with existing RBAC.

Do not backfill original webhook-signature provenance from API retrieval, recover a missing body by signing it locally, or reinterpret 0043 subscription-object observations as original Event envelopes. Legacy rows remain retained and explicitly legacy/unproven until independently linked with new evidence; no migration invents attestations.

## Cross-provenance comparison — G2

Every observation keeps a SHA-256 of its own exact original representation. Verification consumes original webhook bytes before parsing; API bytes and provider request context have a separate integrity trail. Transport byte inequality between these paths is not fraud proof. Comparison is not reserialization of the original or a general JSON canonicalization algorithm.

Recommend a reviewed profile per supported event type and rendering/version pair. Profile requires exact identity tuple, `object=event`, event type, provider-created value and stable underlying object type/ID where present. Resolve direct/Connect account interpretation using G1, not string equality of nullable fields. Unsupported profile, unrecognized semantic fields, missing required field or incompatible rendering produces `incomparable`/`unassessed`, never automatic corroboration. `api_version` selects a profile; a version difference is not automatically an attack.

For subscription profiles, explicitly compare supported historically relevant fields (customer/subscription/item IDs, Price IDs, quantity, status, cancellation/trial/schedule and previous-attribute presence/meaning) under reviewed version rules. These are proposed comparison requirements, not proof that any field gives an exact effective boundary. Missing versus null, unordered arrays, expansion differences and API nullable fields need explicit typed rules. Do not ignore unexplained semantic differences merely to obtain equality. Do not compare a current Subscription resource as if it were a historical Event; preserve it as separate current-state observation.

`corroborated_fields` lists exact matched fields and both evidence IDs; it is not a generic verified event, capture coverage certificate, effective-time proof or tenant entitlement. `conflicted` blocks affected reliance until independent adjudication. `incomparable` and `unassessed` also deny positive reliance. All retain original evidence and append reasoned dispositions.

| Required acquisition case                 | Proposed result and operator behavior                                                                                                                                                         |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Webhook first, API later                  | Retain both, resolve same tuple only with trusted contexts, compare profile, append outcome; no additional authority                                                                          |
| API first, webhook later                  | Same algorithm; webhook does not sign API bytes retroactively and arrival order gives no winner                                                                                               |
| Identical webhook replay                  | Reverify incoming signature; same tuple/representation/context uses committed observation plus delivery record; no duplicate projection job                                                   |
| Same logical ID, conflicting signed bytes | Retain both encrypted representations; conflict hold per HETA-01B, alert with reason; known endpoint rendering/version difference is investigated, not silently waived or called proven fraud |
| Differently serialized API JSON           | Separate integrity digests; typed profile may corroborate fields. Byte inequality alone neither resolves nor condemns it                                                                      |
| Provider-field contradiction              | Append conflict and hold affected logical event/bindings/coverage revision; do not overwrite either source or select latest                                                                   |
| Missing provider event                    | Append retrieval attempt/gap evidence; absence from a list is not absence of a transition or proof of completeness                                                                            |
| Expired retrieval horizon                 | Preserve unavailable/gap result; S4's documented retrieval horizon does not authorize synthetic recovery, inferred bytes or complete history                                                  |
| Multiple receiving accounts/endpoints     | Keep per-observer authorization and provenance; same trusted origin tuple can link; unresolved relationships remain separate unresolved evidence                                              |
| Uncertified historical coverage           | All data remains candidate evidence; HETA-01D states stay non-activating and historicalTierVerified/issuance/redemption stay false                                                            |

Two different Stripe Event IDs can describe one resource change or separate legitimate changes. Retain both identities; downstream reconciliation requires a domain-specific operation/idempotency contract rather than collapsing by object/type. Raw mismatch conflicts and typed comparisons are distinct decisions with explicit scopes; a corroboration cannot erase a previous conflict hold. Release requires independent authorized adjudication and a new revision, leaving the original hold auditable.

## Provider attestation — G3

Propose a private **Provider Context Verification Service** with its own authenticated workload principal and minimal read-only provider credential scopes. No public route accepts an asserted principal, attestation result or deployment account. An independently approved inventory binds deployment/config revision, secret-manager credential version reference, endpoint identity, signing-secret label, provider realm/account/modes and allowed acquisition methods. Inventory approval and provider verification are complementary, not interchangeable.

Verification method proposal (not executed in Block G): authenticated provider account read confirms credential account identity; endpoint configuration evidence binds endpoint/signing context and configured event sources/modes; reviewed account-scoped read confirms Connect access for the exact platform/connected pair and required operation. Preserve provider request IDs, response digests, timestamp and protected evidence references. Successful access only proves the tested scope at verification time, not all permissions, legal ownership or historical uninterrupted authority. A direct account read does not prove livemode; mode needs separately scoped provider evidence and inventory reconciliation. If the chosen provider API cannot prove a claim, the assertion cannot say passed for that claim. No credentials, headers or secret prefixes are exposed in evidence/logs.

Proposed method profile `stripe-v1-context-read/1` must document and verify each claim separately before it can be approved:

1. Read credential principal account through authenticated `GET /v1/account` without an untrusted account override; compare returned account ID with approved inventory. Retrieving an arbitrary known account by ID is not equivalent to establishing the credential principal.
2. Check endpoint ID, source scope, rendering version and secret-manager version linkage against independently approved configuration evidence. A successful synthetic signature test alone cannot establish which real endpoint owns that secret.
3. For Connect, read the approved connected account and demonstrate the exact required Event-read operation under its authenticated account context. Account-object readability alone is not permission to retrieve events. If no suitable read-only probe is available, record that claim unproven and block linkage; do not create financial test activity.
4. Separate allowed-mode policy from observed provider mode. Validate a protected known Event's mode in the same verified context, or use another independently reviewed provider method. An empty list, account response or secret prefix cannot independently prove the requested mode. A failure to establish mode remains unproven; it is never silently replaced by policy expectation.

| Layer                     | Proposed fields / responsibility                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Immutable assertion       | assertion UUID; schema/method version; claim kind; namespace/realm; deployment/config revision; receiver and origin accounts; direct/Connect relation; endpoint/acquisition scope; allowed mode; credential/signing-key version references (not values); verified_at; valid_from/valid_to; recorded_at; result passed/failed; reason codes; trusted service principal; evidence references/digests/provider request IDs; approval reference and lineage |
| Operational configuration | Secret-manager handles, connection/endpoint routing, allowlisted principals, trust registry, explicit mode/realm mapping, approved TTL and comparator versions. Config revisions immutable/audited; secret values remain in vault                                                                                                                                                                                                                       |
| Derived decision          | At evaluation time and knowledge revision: usable/expired/revoked/superseded/conflicted/unproven/failed, reason codes, assertion/incident/config references. Always nonfinancial and recomputed against current revocation head                                                                                                                                                                                                                         |

Account attestation is reusable only for the exact approved account/relationship/acquisition scope; it is not a per-event provider signature. Event ID linkage is checked separately, preventing a valid assertion for the wrong scope/event from being treated as successful event verification. Existing generic `details.result=passed` rows cannot satisfy this contract automatically. A database FK is only a referential precondition. Control stream restrictions need a future additive design; do not stuff an unreviewed new lifecycle into arbitrary JSON and call it enforced.

**Proposed freshness policy requiring explicit G3 approval:** `valid_from=verified_at`, finite half-open `[valid_from,valid_to)`, no more than 15 minutes, no grace and no backdating a fresh assertion. Trusted server UTC must be monitored; unknown clock health or impossible/future-dated times fail closed. A renewal must complete before expiration. Any known credential/config/Connect change invalidates reliance immediately, regardless of remaining TTL. Short TTL bounds undetected staleness; it cannot prove absence of an unobserved change. Historical verification cannot be extrapolated between checks as continuous historical coverage.

Failed attempts are append-only records with redacted reasons, never usable assertions. Outage/expiry blocks scoped reliance; authentic bytes may only enter restricted unresolved quarantine under G5, with no fabricated successful FK. Recovery requires a new successful verification, current approved inventory and resolved incidents. An operator cannot “extend” a prior record by editing dates. Method, TTL, principals, evidence retention and any historical attestation proof remain owner decisions, not deployment instructions.

## Append-only validity, revocation and supersession — G4

Lifecycle events reference immutable assertions and a verified scope, predecessor/head revision, authorized actor, recorded_at, effective_from, reason, evidence and approval. Proposed events: verification passed/failed, scope suspended, revoked, superseded and independently reinstated. Expiration is derived from valid_to, not an in-place update. Original payload, verification assertion and economic histories remain intact.

Recommended resolver accepts `(scope, evaluated_at, knowledge_revision)` and additionally checks the **current** deny/incident head before any new use. Recorded time is what the system knew; effective time is when a change is supported to apply. At ingestion use actual verification/receipt time, not event.created as a backdated verification instant. Historical re-evaluation uses retained evidence and the current incident overlay; a prior as-known result may be shown for audit but cannot bypass newly known invalidity.

Deterministic resolution:

1. Reject missing/untrusted scope, method, principal, evidence, time or inventory; no FK/actor-string shortcut.
2. Read a consistent committed scope head and relevant lifecycle lineage. Unresolved forks, contradictory assertions or incomplete lineage produce conflicted/unproven. No “largest timestamp wins.”
3. Apply current deny incidents intersecting the claimed validity/scope, then causal supersession; deny beats a concurrent usable claim. Unknown compromise start suspends affected historical reliance until bounded independently, without inventing a backdate.
4. Require exactly one applicable passed assertion with `from <= evaluated_at < to`, current inventory binding and no relevant suspension/revocation/contradiction. Expired or superseded references cannot grant new reliance.
5. Return a revision-bound decision; commit of any downstream nonfinancial result must recheck scope/config/incident revisions under the same lock or serializable contract. Cache entries include revision and expiry; stale/unavailable invalidation means deny, never TTL-only trust.

Append commands lock by verified scope and compare expected predecessor; only one successor may advance a derived operational head in the same transaction as the immutable lifecycle event. Losing races retry from the new head. The operational head is a rebuildable index, not rewritten audit history; its future constraints and grants need separate schema approval. If inconsistent heads appear despite controls, freeze the scope and alert.

Credential compromise, changed Connect permissions, account ownership/config changes or later provider contradictions cause immediate suspension/revocation plus a scoped investigation. Reinstatement requires independent successful verification and an explicit authorized new lineage. It never rehabilitates invalid historical evidence automatically. Incorrect historical assertions trigger new invalidation/re-evaluation records referencing affected evidence/coverage decisions, not edits. Financial consequences remain with Split 06/07/08's separately authorized compensating workflows; Block G grants none.

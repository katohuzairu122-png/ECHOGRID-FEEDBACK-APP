## Distinct identities and verified components

HETA-01B §3 defines account + mode + event-ID logical deduplication, identical replay idempotency and quarantine for conflicting same-identity evidence. It does not resolve which account is canonical when receiving and Connect event accounts differ. SQL 0045 instead uniquely indexes `(receiving_account_id, event_account_id, livemode, stripe_event_id, provenance)`. Row UUID is evidence-record identity; digest identifies raw representation; neither alone is canonical logical identity.

Signature verification authenticates exact body bytes under a signing-secret context. Parsed claims and syntactically valid account strings do not establish deployment account/mode, Connect authorization or business ownership. SQL enforces column shape/grouping, not cryptographic truth. In the following matrix, “claimed tuple” means receiver/event-account/mode/event-ID. No SQL fixture is an actual provider verification. API retrieval must retain its own provenance; reserialization need not reproduce webhook bytes. Equal parsed objects/digests alone do not prove provider identity or history completeness.

## Attestation contract assessment

`stripe_evidence_control_events` has a generic actor string, occurrence timestamp, optional approval/commit/window fields and bounded JSON details. Account-provenance kind requires result `passed` or `failed`. Receipt FKs require row existence only. There is no semantic check for method/trusted source, exact account, mode, verification time, validity interval, successful outcome, event kind, evidence provenance, receiver-to-event relationship or authorized Connect access. An occurrence timestamp is not proof of provider verification. `actor` is not authenticated principal authorization; these owner-role tests do not impersonate an application user or establish production permissions.

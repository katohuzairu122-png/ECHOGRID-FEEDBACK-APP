## Architecture decisions

### G1 — Canonical provider identity

**Problem/current:** R1 indexes `(receiver,event_account,mode,event_id,provenance)`. R3 says account/mode/event ID but does not resolve Connect observer versus origin. Receiver/provenance differences can duplicate logical authority; event-ID-only grouping can mix accounts/modes.

**Options:** A receiver + mode + event ID aligns with current reception but fragments Connect observers. B event account + mode + event ID joins observers but omits explicit provider/environment and observation authorization. C explicit provider namespace plus verified origin and separately verified receiver/origin relationship preserves both identities. D globally unique event ID alone is simpler but assumes more than the repository requires and drops mode/scope protection.

**Recommend C, with a two-level contract:** logical tuple `(provider_namespace, provider_realm, origin_account_id, livemode, provider_event_id)`; separate immutable observations hold receiver/endpoint/relationship/provenance. The receiver relationship authorizes an observation's linkage; it is not an extra component that fragments the logical key. Scope initially to reviewed Stripe v1 snapshot events. Direct origin resolves to attested receiving account; Connect origin uses authenticated `event.account` plus verified relationship. Missing/unsupported context stays unresolved. S1/S2 support this distinction; tuple construction is a local proposal, not a documented Stripe uniqueness guarantee.

**Rationale/security:** preserve independent observer evidence while requiring trusted scope before deduplication. No metadata-derived tenant binding. **Economic:** linking cannot authorize a tier or duplicate an award. **Compatibility:** additive mapping over existing UUIDs; keep 0043/0045 untouched, no event-ID-only automatic backfill. **Owner decision:** approve exact tuple, realm registry and supported account/endpoint formats, plus reconciliation with HETA-01B wording. **Acceptance:** identity matrix across direct/Connect, receivers, modes, realms and unresolved contexts. **Status: PROPOSED; implementation BLOCKED.**

### G2 — Cross-provenance reconciliation

**Problem/current:** R1/R2 accept webhook/API rows independently and append no automatic conflict. Digest comparison across paths conflates byte integrity with semantic identity.

**Options:** require identical raw digests (rejects harmless serialization); let newest/API/webhook win (loses evidence and assumes priority); retain observations and use versioned typed comparison (more storage/rule governance). **Recommend typed comparison with immutable outcomes** `corroborated_fields`, `conflicted`, `incomparable`, `unassessed`; no winner by arrival order. Same signed representation mismatch invokes B's conflict hold, with rendering differences investigated rather than labeled fraud. Distinct event IDs are never collapsed merely because object/type match.

**Rationale/security:** audit every original, compare only supported fields and distinguish absence from contradiction. **Economic:** one logical event still conveys zero financial rights; corroboration is not complete history. **Compatibility:** add links/outcomes; do not rewrite original provenance/digest or classify API responses as signed bodies. **Owner decision:** approve comparison profiles, API-version rules, conflict scope/release and retention. **Acceptance:** both ingestion orders and all ten cross-provenance scenarios in the companion contract. **Status: PROPOSED; implementation BLOCKED.**

### G3 — Trusted account attestation

**Problem/current:** generic FK and `result` checks do not establish method, principal, scope or validity. **Options:** FK/claimed passed flag (insufficient); manual approval alone (useful governance, no provider proof); dedicated least-privilege verifier with provider observations plus approved deployment inventory (recommended); per-receipt network verification (latency/outage amplification and still no historical continuity).

**Recommend dedicated verifier:** private authenticated read-only checks, separately attested endpoint/credential/Connect inventory, bounded validity and protected append-only assertion. No credentials in assertions. Method must distinguish account identity, mode evidence and relationship permission; `/v1/account` alone cannot prove all three. Fields/lifecycle are specified in the companion contract.

**Rationale/security:** independently sourced claims and authenticated service identity; internal actor text is not authorization. **Economic:** no eligibility grant. **Compatibility:** generic control rows remain legacy unverified references unless newly and independently validated; do not relabel them. **Owner decision:** approve methods/principals/trust roots, proposed 15-minute maximum TTL/no grace, deployment inventory, privacy/retention and failure policy. **Acceptance:** all fourteen F negative cases plus real-service, expiry and provider-context tests. **Status: PROPOSED; implementation BLOCKED.**

### G4 — Revocation and supersession

**Problem/current:** append-only rows preserve history but do not invalidate stale references. **Options:** mutate/delete original (breaks audit); latest timestamp wins (race/backdating ambiguity); append-only causal revisions with serialized heads and fail-closed resolution (recommended).

**Recommend bitemporal immutable assertions and lifecycle records:** retain verification/effective times and recorded knowledge time, compare-and-set expected predecessor, monotonic per-scope revision, and current deny overlay for compromised/contradictory evidence. Concurrent unmerged heads resolve to blocked, never arbitrary newest. Reverification creates a new assertion; it cannot erase known invalidity.

**Security:** bounded caches and transactional revision checks; retroactive incidents invalidate future reliance on affected history. **Economic:** review incidents without rewriting economic ledgers; Split owners decide any compensating process. **Compatibility:** new append-only stream, not edits to controls/receipts. **Owner decision:** approve effective-time/recovery policy, incident authority, revision/cache protocol and supersession scope. **Acceptance:** race, backdate, compromise, expiration and stale-reference cases. **Status: PROPOSED; implementation BLOCKED.**

### G5 — Receipt, replay and acknowledgement

**Problem/current:** R4 processes a mirror before limited 0043 observation, without 0045 durable capture. SQL uniqueness alone is neither idempotent ack nor durable conflict capture. **Options:** retain synchronous mirror-first path (fails proposed evidence boundary); ack before persistence (loss risk); synchronous provider retrieval before every ack (outage dependency); commit encrypted receipt/conflict/quarantine plus work marker before ack, reconcile asynchronously (recommended).

**Recommend durable receipt transaction**, short and bounded, followed by separately retried nonfinancial reconciliation. Missing trusted scope can persist restricted unresolved evidence, not a forced canonical link. Proposed response matrix is in the delivery plan. No deployed route response changes here.

**Security:** no 2xx on capture/quarantine/key failure; no plaintext fallback; preserve concurrent conflicts. **Economic:** receipt ack is independent of business projection and every financial decision. **Compatibility:** separate cutover plan must avoid double processing and preserve billing behavior; unchanged route is not certified as this design. **Owner decision:** approve ack/quarantine semantics, supported events, payload bounds, alert/on-call/recovery SLA and legacy coexistence. **Acceptance:** commit-loss, concurrent replay, outage and crash tests. **Status: PROPOSED; implementation BLOCKED.**

### G6 — Database and tenant access

**Problem/current:** R5 does not expose live role characteristics. F owner/BYPASSRLS evidence concerns disposable tests only; evidence tables have no RLS. **Options:** shared owner connection/application filtering only (large blast radius); RLS alone with self-set tenant context (context spoofing/owner bypass); separately scoped services and grants, protected verification operations, verified-binding projections and defense-in-depth RLS (recommended).

**Recommend service separation:** nonlogin migration owner; nonowner/non-BYPASSRLS receipt writer, attestation verifier, reconciler and tenant projection reader; restricted forensic reader. Capture cannot mint attestations or read economic data; tenant reader cannot read raw/quarantine evidence. RLS is additional containment, not proof that a pooled role's caller-set setting is authenticated. No public SQL/unchecked SECURITY DEFINER trust boundary.

**Security:** reduce credential blast radius and prevent cross-business enumeration. **Economic:** no role grants on financial writes, no trigger bypass or ownership. **Compatibility:** stage separately provisioned roles/bindings after owner approval, test existing users/connection lifecycle; never repurpose a live Hyperdrive binding in this block. **Owner decision:** approve principal/connection/grant/RLS design, audit access and staged migration/cutover. **Acceptance:** actual nonowner role matrix, two tenants/branches, pooling leakage and forbidden writes. **Status: PROPOSED; implementation BLOCKED.**

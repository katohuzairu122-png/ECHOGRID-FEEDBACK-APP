## Problem and scope

`apps/api/src/billing/allocation-freeze.transaction.ts` validates integrity, locks reservations and writes a complete batch only in privileged disposable fixtures. It does not authenticate the invoice or caller. Both migration 0052 allocation triggers reject every INSERT/UPDATE/DELETE/TRUNCATE. Therefore calling that writer from a route or granting application INSERT is not a supported append path.

The proposed capability would append one immutable, internally consistent allocation batch for an independently authenticated binding. Its success would establish durable integrity evidence only. `providerVerified=false` and `consumptionAuthorized=false` must remain literal outputs and SQL constraints. It would not create a provider attempt, authorize a provider write, release or consume credit, execute compensation, certify HETA history, or mutate accounts/lots/ledger/reservations.

## Authority and authenticated binding prerequisite

Split 06 retains source consent, receiving-business acceptance, settlement and reversal evidence. Split 07 retains awards, accounts, lots, disputes, recovery obligations and credit movements. Split 08 retains invoice eligibility, allocation evidence and provider reconciliation. Authentication and tenancy remain server-owned.

The application-facing request may identify the requested business action and correlation key. It cannot supply authoritative business identity, monetary values, eligibility, balances, permissions or a trusted invoice binding. Resolve authenticated identity and business permission on the server; reject scope substitution before exposing another tenant's existence. A UUID, a TypeScript type, a caller-generated digest or a mutable session variable is not proof.

A separately approved immutable binding source is required before implementing an operational append path. It must correlate:

| Binding field                                   | Required trusted relationship                                                                                                                                                |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authenticated principal/service and business    | Existing authentication and permission source; exact business scope and authorized operation                                                                                 |
| Provider account and test/live mode             | Server-owned configured scope with independently established provider identity; no fallback across accounts/modes                                                            |
| Customer and subscription                       | Business-owned subscription identity and immutable historical correlation; a current subscription mirror alone is insufficient historical proof                              |
| Invoice, currency and supported policy versions | Same authenticated provider scope, customer and subscription; authoritative source/effective-time references                                                                 |
| Reservation and invoice intent                  | Persisted original one-unit reservation, its business/intent binding and retained source-domain evidence                                                                     |
| Eligible base and capacity                      | Validated source evidence under existing policy, including this batch's reserved units; never post-reservation available balance treated as original capacity                |
| Evidence identity, freshness and revocation     | Immutable provenance/version, checked-at/effective boundary and server-owned validity rules; missing, stale, revoked, conflicted or unproven required evidence denies append |

No current table is asserted to satisfy this complete prerequisite. `business_subscriptions` is a current read-optimized mirror; the stored allocation verifier can reconstruct self-consistent data without an independent source. Neither authenticates the full tuple. HETA interval completeness/certification and required historical-tier verification remain governed by their sources, with no new approval flag or inferred certified state.

Two binding persistence choices remain for architecture approval: an immutable authenticated binding reference, or explicit scoped columns/keys with equivalent immutable provenance. The present `(business_id, invoice_ref)` uniqueness omits account/mode. Preserve it until the chosen design proves that different provider scopes cannot alias a freeze, including on replay. A conflicting scope must reject rather than widen a key, select a second identity or silently reuse an invoice reference. A binding schema, evidence freshness interval and trusted reader must be recorded and tested before dependent implementation; this document invents none of them.

## Proposed database capability boundary

The design to evaluate is one narrowly defined database entry function, owned by a dedicated NOLOGIN role with no application membership, exposing only the validated whole-batch operation. The runtime caller receives only the exact EXECUTE capability after separate approval; it receives no direct table mutation, ownership, DDL, trigger-control or replication privileges. PUBLIC receives no EXECUTE or table capability. Ordinary readers remain business-scoped through a separately reviewed access path; an unscoped table SELECT grant is not the product API.

Any future SECURITY DEFINER function must have a fixed trusted search path, schema-qualified objects, a fixed typed signature, bounded inputs, no caller-selected relation/function names, no dynamic SQL assembled from request text and no ability to select an arbitrary role. The owner must not own the tables or unrelated functions, and must have only the minimum validated storage/read/locking privileges. No application role may SET ROLE to that owner or CREATE/replace functions in the trusted schema. Review default privileges and role memberships, not only explicit grants.

Reservation row-locking privileges require their own PostgreSQL proof. Do not solve a locking-permission failure through broad economic mutation grants, table ownership, session replication changes or disabling an economic guard. If a least-privilege locking boundary cannot be established while preserving existing reservation guards, dependent implementation stops for architecture review.

Migration 0052's unconditional INSERT denial cannot coexist with a working append into those tables. This is an explicit future gate, not an instruction to bypass a trigger. A separately approved additive migration would have to replace only the allocation INSERT admission rule with a database-verified narrow execution identity; UPDATE/DELETE/TRUNCATE remain unconditional denials. The admission guard must be SECURITY INVOKER so it observes the actual execution identity, not elevate every caller itself. A dedicated function owner must be exclusive to the reviewed entry function and unreachable by other callable helpers. No session flag, caller-set claim, writable authorization table or credential exported to the client may confer that identity.

That future rule must deny direct application INSERT even after accidental INSERT grants. The function owner must not become a general login or reusable mutation role. If role/function isolation cannot be proven, retain unconditional INSERT denial. All current triggers and privileges remain unchanged by this proposal; no guard transition is authorized here.

## Proposed append operation

The conceptual inputs are a server-resolved authenticated binding reference, the exact original set of reservation references and a stable request correlation identity. The server must not accept a client-computed artifact as authoritative. A future exact signature and binding-reference format depend on the prerequisite decision above; no callable API is defined today.

The operation must:

1. Verify caller business permission against the trusted binding; validate the complete provider/business/invoice/subscription tuple and required source validity. Fail closed on incomplete or conflicting evidence. No provider network request occurs inside a database lock transaction; a separately authenticated source snapshot and its revocation/version checks must have an approved race/freshness model.
2. Acquire the complete batch's reservation locks in canonical persisted ID order, matching reservation-before-intent ordering used by `beginApply`. Recheck exact tenant, intent, reserved state, one unit, expiry and absence of any persisted provider attempt. The global order with settlement/claim, decision/lot, account, recovery and reversal writers remains separately gated; do not acquire those locks in an invented order.
3. Read authoritative amounts/capacity and supported policy from the trusted binding, then independently compute and validate S08-AGG-ROUND/1. Retain one aggregate floor, positive shares, canonical residual assignment, one to ten reservations and exact conservation. Reject the whole batch rather than silently drop a reservation or choose another rounding policy.
4. Enforce every destination's numeric limits before writing: SQL bigint must remain lossless, JavaScript values must be safe integers, and amounts destined for existing int4 saga fields must fit those fields. An inert bigint column's ability to store a larger integer is not permission to pass it to a narrower component. Do not widen existing columns or policies in this block.
5. Compute the canonical versioned digest independently inside the trusted boundary. SQL JSON serialization must not substitute for the published positional UTF-8 encoding; whitespace, property order, numeric spelling and Unicode behavior must match golden vectors. A database encoder/validator is not currently implemented or certified. Trusting a digest supplied by application JSON is insufficient.
6. Atomically insert parent, all children and minimal immutable append audit evidence, or compare the complete existing envelope. Validate tenant FKs, uniqueness, exact ordered child set, child count/sum, original intent references, currency/policies, stable provider keys and equality between relational and artifact values. No caller-accessible intermediate operation may leave an incomplete batch committable.
7. Perform the final locked server-clock expiry check immediately before transaction completion. Preserve the existing distinction from physical WAL commit time. Return only the original freeze identity/digest, replay classification and false authority flags. A response is not provider success or financial authorization.

A single database call must bind all validation and writes to its transaction. Exceptions must escape and roll back the full operation; do not catch a failed validation and commit a parent, child subset or success audit. Cancellation/timeout must have the same atomic outcome constraints. An outer caller must not be able to commit partial internal work or execute an independently privileged child-insert function.

The function and audit must not read credentials, retain raw provider payloads, expose customer contact/payment information or return private cross-business relationships. Audit records should contain versioned references/digests, service identity, reason/outcome, request identity and server time, with access and retention governed by existing policy. A new audit schema/retention decision requires review; no storage is invented in this document.

## Replay, conflict, revocation and supersession

| Situation                                                                      | Required behavior                                                                                                                                                    |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identical authorized request, same live binding and reservations               | Return the original complete freeze/digest; no replacement parent, child or provider key                                                                             |
| Same request identity or invoice/reservation key, changed scope/amount/content | Reject and retain the original evidence; no silent update, rebind or replacement                                                                                     |
| Lost COMMIT acknowledgement                                                    | Reconnect and inspect durable identity; if present, compare every field and return the original result; if absent, retry the same operation under all current checks |
| Reservation expired before a new append or while waiting                       | Reject new append at the final locked check; preserve any committed history                                                                                          |
| Durable freeze found after expiry/revocation                                   | Evidence remains readable through an authorized lookup; it grants no new append/attempt or provider operation. Preserve existing strict freeze expiry behavior.      |
| Existing provider attempt, including unknown outcome                           | No new freeze or replacement attempt. Existing attempt recovery/reconciliation retains its original key under its existing service contract.                         |
| Missing or partial storage/binding; incompatible schema                        | Reject new append. Never fall back to fixture behavior or an unguarded writer.                                                                                       |
| Conflicting or revoked historical evidence                                     | Preserve evidence and dispute/recovery obligations; deny new dependent work. Do not rewrite past invoices or allocation rows.                                        |

Append audit is immutable. A successful replay may produce a separately deduplicated audit observation if its reviewed contract requires it; it must not create another allocation or imply a second financial action. A rolled-back success audit cannot prove a denied operation; failure observability must use an independently authorized, redacted path and may never force a partial commit.

Current invoice/reservation uniqueness forbids allocation replacement. A future supersession model requires explicit immutable predecessor, reason, actor/version and server-time evidence with no ambiguous/forked interpretation. This proposal introduces no supersession table, UPDATE, DELETE, TRUNCATE, release permission or second provider identity.

## Acceptance plan before an append implementation can be approved

| Area                      | Required disposable evidence                                                                                                                                                                                                                                                                    |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authenticated binding     | Missing/fabricated/stale/revoked/conflicted provenance; wrong account/mode/business/customer/subscription/invoice/currency/policy; evidence changes while a worker waits; no cross-tenant existence leak                                                                                        |
| Restricted database roles | Direct I/U/D/TRUNCATE denied, including accidental grants; function-owner impersonation/membership and schema/function replacement denied; malicious search path/GUC and alternate helper calls cannot acquire append identity; required row locks succeed without economic mutation capability |
| Whole-batch invariants    | Missing/extra/duplicate/reordered children, mismatched sums/counts/digests/envelope/intent/key, unsupported versions, zero allocation and limits deny atomically; independent golden-vector encoding agrees with S08-AGG-ROUND/1                                                                |
| Numeric boundaries        | Safe-integer and bigint parsing, int4 destination edges, overflow, negatives and forbidden coercions; exact conservation with no truncation                                                                                                                                                     |
| Concurrency and recovery  | Overlapping batches, opposite input ordering, concurrent same/conflicting requests, freeze versus attempt, expiry/revocation during waits, rollback after every insertion/audit stage, backend interruption and both COMMIT acknowledgement outcomes                                            |
| Immutable history         | Direct correction/cascade/truncate denied; replay preserves original ID/content; no ambiguous supersession or replacement operation after unknown outcome                                                                                                                                       |
| Migration/privileges      | Fresh install, populated 0052 upgrade, incompatible existing objects, failure/retry, full snapshot/journal/hash parity and unchanged protected migrations; catalog and default-privilege/membership assertions for every new capability                                                         |
| Domain conservation       | Before/after accounts, lots, reservations, immutable ledger and applications unchanged; no provider attempt, Stripe call, issuance/redemption/consumption, compensation or settlement occurs                                                                                                    |
| Regression                | Preserve the 27 inert-migration tests and existing recovery/tenant/evidence tests; adapt the migration suite to pin 0052 before introducing any later journal entry; run lint, typechecks, HETA, full PostgreSQL plus isolated award suites and applicable CI                                   |

Owner/superuser fixture success is not restricted-role authorization. Fake-provider results are not provider authenticity. Passing CI is not production role/RLS, activation or deployment certification. Keep the five economic guards, candidate/migrated append-only safeguards and HETA authority gates independently asserted.

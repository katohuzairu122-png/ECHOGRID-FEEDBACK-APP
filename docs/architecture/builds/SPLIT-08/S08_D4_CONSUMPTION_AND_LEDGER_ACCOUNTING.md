## Decisions that are MINE and need owner ratification

The documents leave these open ("D4: ledger vocabulary ... undecided"). I made the smallest consistent choice; each is reversible before activation.

1. **Ledger vocabulary.** No existing entry type can record a unit leaving the buckets while keeping the audited identity, so two types were added (above). A consumed-credit reversal cannot reuse `reverse` (it would double-count a unit that already left) and so uses an informational `consumed_reversal`.
2. **Consumption is refused while an award dispute hold is active.** The unit stays reserved until the hold resolves. (A provider effect may already exist; this is a bookkeeping hold, not a reversal of money.)
3. **An effect confirmed after the reservation's own deadline is not recorded or consumed.** It fails closed for review rather than silently consuming an expired reservation.
4. **Only an `active` subscription is eligible** to receive a recorded application (the documents say "verified active/eligible subscription"; "eligible" is read as `active`).
5. **The allocation's amount, invoice and currency must match the saga intent.** The allocation policy itself is pinned to `S08-AGG-ROUND/1` by the existing database CHECK; it is deliberately *not* compared with the benefit policy (`PC-BENEFIT/1`), which is a different concept.
6. **The application key is per reservation, not per invoice.** 0042 made it `UNIQUE(business_id, invoice_ref)`, which contradicts the approved aggregate allocation (up to 10 reservations on one invoice): a second reservation could never be recorded. It is now `UNIQUE(business_id, invoice_ref, reservation_id)`; the number of applications for an invoice is bounded by its frozen allocation items. This changes a constraint from a frozen migration, so it needs your ratification.

## What this does NOT do (still blocked or unbuilt)

- **No activation.** The guards are not removed; `consumption_authorized` on allocation freezes stays false by CHECK.
- **No provider write path.** Nothing here calls Stripe or applies a benefit; the saga reaches `consumed` only from a provider observation, and no mutating provider exists.
- **No release path.** `release` still throws `SPLIT08_RELEASE_AUTHORITY_NOT_ESTABLISHED`.
- **D1, D3 and the economic defaults remain owner decisions** (benefit instrument beyond the development choice, settlement-evidence fields, intervals/trials/rounding sign-off).
- **No end-to-end test against real Stripe test mode**; the 17 PIC/1 activation scenarios remain NOT CERTIFIED.
- **A revoked award with an applied benefit is a dead end.** A dispute hold survives a `revoked` resolution and the revocation plan is approved but never executed; with a benefit already applied, the unit stays reserved and cannot be released (release is unbuilt). The writer now refuses to record during a hold, but the policy for "revoked + applied" is an owner decision.
- **The application row is not verified at INSERT** (existing tests exercise the 0042/0047 constraints directly on bare rows). The evidence is judged at consumption, by the writer, the consumer and the reservation trigger; a forged application without a reconciled saga and matching allocation cannot be consumed.
- **Recovery-offset interplay** (a later vesting credit offsetting the new obligation) uses the existing, unchanged offset writer; it is not re-tested here beyond the ledger identity.

### D4-06 exception record (frozen 0042 constraint `billing_partner_credit_applications_invoice_once`)

0042 is not edited (`git diff origin/main` of 0041/0042/0048 is empty); migration 0053 drops the old constraint and adds `UNIQUE (business_id, invoice_ref, reservation_id)`.

1. Several approved reservations on one invoice each receive exactly one application: test "one invoice with TWO reservations" uses the real aggregate freeze (300 + 300) and records and consumes both.
2. The same reservation cannot be applied twice: `reservation_id` carries its own `UNIQUE` since 0042 (`billing_partner_credit_applications_reservation_id_key`), unchanged; the new key is therefore the *only* weakening and it only relaxes the per-invoice limit. Test: a replay returns the same row, and a second insert for the same reservation is refused with a duplicate-key error on the same and on another invoice.
3. Applications correspond to frozen allocation items: a reservation without a frozen item cannot reach an application (the saga cannot be applied without a frozen allocation, the writer refuses `ALLOCATION_MISSING`), and the set of applied reservation ids for an invoice equals the set of its frozen item reservation ids (test). The database does not verify the application row at INSERT (a forged row is stopped by the write guard, and cannot be consumed: the reservation trigger needs the matching saga and item).
4. Business isolation: the key includes `business_id`; another business cannot reach the reservation (`S08_APPLICATION_UNKNOWN_RESERVATION`); composite tenant FKs from 0042 are unchanged (test).
5. Compatibility: on a database migrated to 0052 holding an existing application row, 0053 applies in one transaction (row preserved, all FKs and the other unique keys intact), a rolled-back 0053 leaves the old constraint and none of the three D4 triggers, and the 0041/0042/0048 write guards remain enabled and still deny writes. No code or query referenced the old constraint name (repository search).
6. The key is only superseded by a new migration; 0042 is untouched.
7. The exception and this evidence are recorded here and in PR #206.

### PostgreSQL 18 baseline discrepancy

`s08-allocation-migration` "retains tenant FKs ..." expects SQLSTATE `23503` for deleting a frozen parent that has a child; PostgreSQL 18.6 returns `23001` (`restrict_violation`). The same single failure occurs on untouched `main` (2e69d68) and on this branch with identical assertion text and SQLSTATE; PostgreSQL 16 returns `23503`. A direct probe confirms the cause: for an FK declared `ON DELETE RESTRICT`, PG16 raises `23503` and PG18 raises `23001`, while a default (no action) FK raises `23503` on both. The 0052 child FK is `ON DELETE RESTRICT`. Determination: **pre-existing, caused by a PostgreSQL 18 behaviour change, not by D4.** The assertion was not weakened; the owner should decide whether the test should accept both codes before PostgreSQL 18 is targeted (the CI service container is not PostgreSQL 18).

### Outstanding risks (documented, not implemented)

- **Revoked award with an applied benefit.** `hasActiveDisputeHold` treats `open` and `revoked` (approved plan, not executed) as a hold. D4 refuses to record or consume under a hold, release is unbuilt (`SPLIT08_RELEASE_AUTHORITY_NOT_ESTABLISHED`) and revocation execution is unauthorized, so a credit whose benefit was applied before the revocation stays `reserved` indefinitely. Proposed fail-closed policy for separate owner approval: (a) keep the unit reserved and the award held; (b) classify the pair "revoked + provider effect applied" for operator review with the same read-only evidence as D4-03; (c) resolve only through a dual-control, audited, separately authorized stage that either executes the revocation (recovery obligation, as for a consumed reversal) or records an owner-approved exception; (d) never release or consume automatically, never refund automatically.
- **Application INSERT evidence.** Untrusted application rows cannot create consumption authority: the write guard denies inserts outside a disposable database, and even a forged row is useless because the reservation trigger requires the reconciled saga (same effect and invoice) and a matching frozen allocation item; tests bypass the service and the database refuses.
- **TRUNCATE gap (not implemented).** A catalog query on a freshly migrated database shows ten write-guarded Split 07/08 tables with no `BEFORE TRUNCATE` trigger: `benefit_application_intents`, `billing_partner_credit_applications`, `partner_credit_accounts`, `partner_credit_award_decisions`, `partner_credit_ledger`, `partner_credit_lots`, `partner_credit_multiunit_lot_allocations`, `partner_credit_multiunit_movements`, `partner_credit_recovery_obligations`, `partner_credit_reservations`. (The earlier figure was nine; this query finds ten; the discrepancy is for the owner to settle when that block is authorized.) Row-level guards do not fire on TRUNCATE, so the gap remains. D4 adds no new table and does not widen it. Not addressed here.

## 2. Reconciliation of the decisions with the code

### 2.1 Facts that make the decisions workable (and their limits)
- **G2 is provable.** Each recovery offset is an immutable ledger entry (`recovery_offset`, negative units) carrying the vesting credit's `decision_id`, with metadata `{ obligationId, reversalRef, offsetUnits }` and the per-obligation key `partner-recovery-offset:v1:<settlementRef>:<obligationId>` (`applyRecoveryAtVest`). The offset per vesting credit is `min(outstanding, 1)`, so at most one unit and one entry per decision. **Exactness has to come from that evidence, not from the table CHECK:** the obligation CHECK `units_outstanding <= units_due` only stops exceeding the cap; it does not stop restoring onto the wrong obligation or restoring twice. So restoration must (a) read the amount and the `obligationId` from the decision's own `recovery_offset` entry, (b) be limited to one restoration per decision by a unique index on the new evidence entry, and (c) verify the account's `recovery_due` equals the sum of outstanding units before and after (the existing equality assertion runs only at vest). **No database trigger guards obligation updates today** (only the 0041 insert guard and the truncate denial), so the executor's restoration is ungated at the database level; a guard on obligation updates belongs in the design.
- **Lock order.** Settlement, then claim, then decision, lot, account, **recovery obligations** (`FOR UPDATE`, ordered by creation then id, as in `applyRecoveryAtVest`), reservation; the saga intent and the dispute rows are read or locked after, in one fixed order. The claim lock exists in vest, reserve and reversal; the executor either never locks the claim or locks it before the decision.
- **The dispute hold is application-level; no database trigger checks it**, so the R2 exception is technically possible without weakening any database guard. Migrations 0053, 0056 and 0057 stay satisfied if every case writes its evidence first (consumed reservation before lot consumed; the reversal entry before lot reversed; a terminal time not earlier than the application time).
- **Exactly-once comes from the locks plus a state re-check under lock; a canonical idempotency key is defense in depth.** If the executor and a Split 06 reversal both write their reversal-class entry under `partner-reversal:v1:<settlementRef>`, the unique ledger key backs the locks, and the compensator's existing `already_reversed` branch (which looks that key up and checks only that the row exists) recognises an executed revocation. In the two orders: executor first, then reversal gives `already_reversed`; reversal first, then executor gives a final `superseded`.
- **A zero-unit ledger entry is impossible** (`units <> 0`), and the entry-type CHECK is a closed list recreated in 0053; a new type means dropping and recreating the CHECK, the TypeScript enum and the schema CHECK, with a per-decision unique index like 0053's. The existing `admin_adjustment` type cannot be reused for these cases: it is excluded from the net but carries no per-decision uniqueness or evidence meaning, so the audit could not tell it from an operator edit.

## 3. Cross-cutting architecture

1. **One shared unwind routine** used by both the compensator (inside the Split 06 transaction) and the executor (its own transaction), with the case table below as its only logic. Two copies would diverge. Every multi-step case (E1, C2) runs in a single transaction.
2. **Ledger and obligation metadata, compatible with the existing audit.** The audit joins an obligation's `reversal_ref` to the entry's `metadata.reversalEventId`. A revocation execution therefore writes the **correction id into both** `reversal_ref` and `metadata.reversalEventId` (both are uuids, unique per obligation), and adds `source: 'revocation'` and `correctionId` keys so the cause stays distinguishable; Split 06 reversals keep `source: 'settlement_reversal'`. The audit's existing join then passes unchanged for F and E1; the audit is extended only for the new entry types and, optionally, to report the source.
3. **Canonical reversal key** `partner-reversal:v1:<settlementRef>` for every reversal-class entry (section 2.1).
4. **Ledger vocabulary (migration, Block 1):** a non-zero informational type for "reversed with no balance effect" (G1 and the expired case of R10) and one for "recovery restored" (G2), each excluded from the net identity like `consumed_reversal`, each with a CHECK, a per-decision unique index and audit checks; the TypeScript enum and schema CHECK are updated with them, and the 0057 lot rule and the audit accept exactly those. **Every other reader of ledger types or lot states must be inventoried and updated**: `partner-credit.repository`, `ce1-tenant-integrity.verifier`, `partner-credit-application-integrity.reader`, `partner-credit-terminal-evidence.reader`, `partner-consumption-authority.contract`, and the multi-unit conservation audit.
5. **Obligation update guard:** a trigger so that obligation updates occur only with matching ledger evidence (today they are unguarded).
6. **Evidence-first write order** in every case so migrations 0053, 0056 and 0057 stay satisfied.
7. **Execution storage (Block 2):** append-only **attempts** (many; `blocked` with reason, retried later) and one immutable **final execution** per decision (partial unique index on the decision for `executed` and `superseded`), recording the actor identities; the R5 distinctness trigger (section 2.2); every final outcome moves the decision to `reversed` (and, for G1, the lot to `reversed`). New tables get a write guard and a `BEFORE TRUNCATE` trigger that is `ENABLE ALWAYS`, like every protected table.
8. **Alerting (R7):** a read-only detector listing disputes and revoked plans older than a threshold, bucketed by escalation interval, excluding withdrawn plans; it writes nothing and resolves nothing. Delivery waits for O5.

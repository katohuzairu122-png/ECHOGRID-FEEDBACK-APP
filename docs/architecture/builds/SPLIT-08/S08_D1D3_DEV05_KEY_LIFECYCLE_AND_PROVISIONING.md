# S08 D1/D3-DEV-05 — Signing-key lifecycle, least-privilege migration and provisioning (development record)

Status: DEVELOPMENT ONLY, INERT. Financial activation: NO-GO. Synthetic keys, roles and databases only. Stacked on DEV-04 (PR #224, unmerged when this was written): no new migration number; it amends the still-unmerged 0061.

## What was added
1. **Migration 0061 now applies for a non-superuser owner.** Proven on a fresh cluster (migrator with CREATEROLE only, creating the roles itself) and in the integration suite (roles pre-existing, migrator holding ADMIN OPTION). A non-superuser could not `ALTER FUNCTION ... OWNER TO settlement_authority_reader` (needs SET on the role and CREATE on `public`). 0061 now grants both **temporarily**, only to a non-superuser migrator that lacks them, and revokes them in its last statement; a membership the owner provisioned beforehand is never revoked. Result: owner has no SET/INHERIT on the internal role, the role has no CREATE.
2. **Trusted-key registry from configuration.** `parseTrustedSigningKeys(json)` loads `{"key-id":"<64 hex Ed25519 public key>"}`; anything malformed (duplicates, wrong length, bad ids, non-object) returns `undefined`, which makes the gate refuse everything. Key ids are stricter than the DB check (no leading separator). Rotation = add the new id (overlap), re-record under the new signer, remove the old id; revocation = remove the id.
3. **Rotation/revocation tests (K1–K5).** Overlap accepts both keys; removing the old key stops its evidence and moves nothing until the new key re-records (old rows remain, append-only); a genuinely signed newest row from a revoked key never authorizes; case or whitespace variants of a key id are different keys.
4. **Deterministic lock tests (L1–L2).** The recorder and consumption wait on the reservation row lock (observed through `pg_stat_activity`, using FOR NO KEY UPDATE so the FK check cannot mask a missing explicit lock); nothing is written while waiting; a revocation racing a consumption never leaves a consume the newest evidence disallows.
5. **Provisioning template** `apps/api/scripts/sql/settlement-authority-provisioning.sql` — NOT in the journal, applied by nothing. Edits two login names; refuses unset/missing/non-login/privileged/identical logins and any login already holding the other duty; grants the application login `settlement_consumer` (INHERIT, no SET) and the recorder login `settlement_recorder` (SET, no INHERIT). Tested end to end (P1, M3, M4).
6. **Recorder change found by that test:** a recorder login that does not inherit its role could not call the verification function for its replay lookup, so the recorder now switches to `settlement_recorder` before the lookup as well as the INSERT, and resets afterwards.

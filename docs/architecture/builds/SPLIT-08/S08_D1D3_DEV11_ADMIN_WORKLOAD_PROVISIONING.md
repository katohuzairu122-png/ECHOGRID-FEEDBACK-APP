| Area | Module | Rule |
|---|---|---|
| Administrator session | `admin-session.ts` | `authenticateAdminSession(deps, authorizationHeader)` reuses the existing HS256 access token (`verifyAccessToken`) and persisted records; there is no second provider. It resolves the administrator from the `users` row (`status = 'active'`, `platform_role = 'admin'`, not deleted), rejects impersonation tokens, requires a live (unrevoked, unexpired) `refresh_tokens` session record, and fails closed on any error. The only way to get a `TrustedAdminContext` (frozen, branded, WeakSet-registered; opaque session id = digest of the token). |
| Lifecycle service | `read-authorization-admin.ts` | `propose / approve / revoke / status / auditHistory` take a context and derive the actor from it; there is no actor parameter. Forged, cloned or stale contexts are refused before the database. The DEV-10 database guard re-verifies the administrator on every transition, enforces distinct proposer/approver, terminal revocation, expiry, row locks, and writes the audit trail. Approval stays **disabled** (policy switch) and no route exposes any of this. |
| Workload identity | `workload-identity.ts` | `createWorkloadAuthority({source, environment, clock})` reads trusted runtime configuration only; the identity binds workload id, environment, Stripe test account, realm, method scope (only the two performable methods can be configured), credential reference, signing-key purpose, validity and revocation, and is re-read on every check (expiry/revocation apply to the next read). `gateForWorkload` builds the only `ReadGate` for the workload; its `workloadCheck` runs before the authorization store and before any credential resolution. |
| Credential custody | `credential-custody.ts` | Reference / descriptor / secret provider / validation / binding are separate. `sourceFor(identity)` needs a genuine workload identity and re-checks the workload authority on every resolve before touching the secret provider. Test-mode keys only, expiry, revocation, account/workload binding, rotation overlap (newest valid version; previous version as fallback), no value in audit events or errors. |
| Signing-key custody | `signing-custody.ts`, `trusted-runtime.ts` | Directory of public key records (purpose, version, issuance window, retained-verification deadline `verifyUntilMs`, revocation). `activeSigner(purpose)` picks the newest valid version and re-checks the directory on every signature. Verification uses `verifyUntilMs` (retained-key policy); a revoked key verifies nothing; unknown ids and wrong purposes are rejected; synthetic keys can never verify as `REAL_NETWORK`. |
| Transport | `transport.ts` | A credential source may name why it refused (`CREDENTIAL_REVOKED`, `CREDENTIAL_WORKLOAD_NOT_AUTHORIZED`); anything else is "unavailable". |

## Known limits (honest disclosure)
1. **No HTTP route or middleware** wires `authenticateAdminSession`; no operational approval path exists (owner decision on the approval policy). The access token carries no session id, so liveness is "the user has at least one unrevoked, unexpired refresh-token record"; a revoked session whose sibling session is live is not distinguished (existing token design, unchanged).
2. Workload configuration, credential descriptors, the secret provider and the key directory are **interfaces with test fakes**; production configuration, secret storage, key custody and runtime identity provisioning are owner decisions.
3. The `scope` check in `requireFreshAdmin` is unreachable by construction (contexts are only minted with that scope): an equivalent mutant kept as defence in depth.
4. Everything remains subject to the DEV-10 limits (key ring is trusted configuration; proofs not persisted).

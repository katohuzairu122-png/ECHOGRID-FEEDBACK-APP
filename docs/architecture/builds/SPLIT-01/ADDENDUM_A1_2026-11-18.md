## 4. Owner decisions (2026-11-18)

**D1 — Redeem control (accepted deviation from invariant 9, `redeem_reward` only).** `redeem_reward` is in the spec and the schema CHECK but has no writer. Customer redemption runs on the customer JWT (90-day lifetime at `e620dec`, `CUSTOMER_ACCESS_TOKEN_TTL_SECONDS`) and the cashier confirms the redemption code at the counter. Decision: keep that control, add the membership and account gate, add no customer step. `COMPLETION_REPORT.md` §9 locks a short-lived authorization *primitive*, which exists; the spec's invariant 9 says sensitive actions *use* it. This addendum records the deviation and does not amend the frozen spec. Revisit if redemption ever completes without counter confirmation.

**D2 — Withdrawal.** Revoking the `join_loyalty` consent ends the membership (`left`), stops earning and spending, and keeps the points balance. Re-joining with fresh consent restores access to it. `POST /customer-memberships/:businessId/leave` does the same thing. Every other consent purpose is a plain revoke.

**D3 — Data check.** One read-only SELECT of eight counts on production and staging was approved and run (§9).

## 5. Membership state model

| State | Written by | Earn / spend | Customer sees |
|---|---|---|---|
| none | — | Refused | 409 `MEMBERSHIP_REQUIRED`; join offered |
| `active` | join (new, or re-join from `left`); 0034 backfill | Allowed (account must be active and linked) | — |
| `left` | leave endpoint; withdrawal of `join_loyalty` consent | Refused | 409 `MEMBERSHIP_REQUIRED`; join offered (fresh consent) |
| `suspended` | 0034 backfill only (mirrors suspended accounts) | Refused | 403 `MEMBERSHIP_SUSPENDED`; join not offered; join call gives 409 `MEMBERSHIP_NOT_REACTIVATABLE` |
| `pending`, `business_exited`, `closed` | Nothing writes them today (reserved) | Refused (fail-closed) | 409 `MEMBERSHIP_UNAVAILABLE`; join not offered |

A suspended loyalty account is treated like a suspended membership. An account whose `membership_id` is null (legacy) is accepted; one that points at a different membership gives 409 `MEMBERSHIP_MAPPING_CONFLICT`. The membership is judged before the account. One pure function (`evaluateMembershipGate`) decides for check-in, redeem and issue, and any status it does not recognise is refused.

## 6. Concurrency model

- **Relationship lock.** `pg_advisory_xact_lock(hashtextextended('customer_business_relationship:<customer>:<business>', 0))`, taken first by join, leave and consent withdrawal, so those three never interleave for one customer and business.
- **Spend and earn paths** (check-in transaction, redeem, issue) read the membership `FOR SHARE`. A leave or withdrawal that races them is strictly ordered: the spend waits, then sees `left`. Spends do not block each other. Lock order is membership, then reward, then account.
- **Staff `recordPurchase` and `adjustPoints`** take neither lock. They lock the account first; adding a membership read there would reverse the lock order and risk deadlock.
- Checked on PostgreSQL 16 during development: without the advisory lock two sessions collide on `business_customer_memberships_customer_business_key`; with it they serialise and leave one row.

## 8. Deploy order, compatibility and rollback

No migration. The schema is unchanged since 0034 (head 0080 at the baseline).

1. **Web first, then API.** The new API refuses a join without `consentAccepted: true` (400); the previous API ignores the new fields, so the new web works against either.
2. **Rollback in reverse:** API first, then web.
3. Data written by the new code is readable by the previous code: a `left` membership is not active there (`findActive`) and re-join reactivates it.
4. Response bodies of the four membership/join endpoints lose internal fields (§12). No client in this repository reads them. Confirm for any external consumer before release.
5. Run `split01-reconcile.mjs` against each environment before and after deployment (§11).

## 12. Behaviour changes to know about

- `POST /customer-memberships/join` and `POST /loyalty/me/join` require `consentAccepted: true` and a `consentVersion` of `v1` (400 `VALIDATION_ERROR` otherwise). `/loyalty/me/join` no longer accepts a bare `{ businessId }`.
- `GET /customer-memberships`, `GET /customer-memberships/:businessId`, both join endpoints and the new leave endpoint return DTOs. Removed from responses: `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, `isDeleted`, `deletedAt`, `deletedBy`, `suspendedAt`, `businessExitedAt`, `closedAt` on memberships; `membershipId` and `referredByCustomerId` on accounts. `leftAt` is added.
- Check-in by a suspended member is 403 `MEMBERSHIP_SUSPENDED` (was 409 `MEMBERSHIP_REQUIRED`).
- Redeem and issue refuse a missing, left, suspended or unavailable membership and a suspended account. A legacy account with no membership is refused with 409 `MEMBERSHIP_REQUIRED`.
- A malformed `businessId` or consent id in a path is 404 (was 500).
- New codes: `MEMBERSHIP_SUSPENDED`, `MEMBERSHIP_UNAVAILABLE`, `MEMBERSHIP_NOT_LEAVABLE`, `MEMBERSHIP_JOIN_CONFLICT`, `LOYALTY_ACCOUNT_UNAVAILABLE`, `CONSENT_IDEMPOTENCY_CONFLICT` (join), `ACTION_AUTHORIZATION_IDEMPOTENCY_CONFLICT` and `INVALID_AUTHORIZATION_TTL` (service level).
- The action resolver offers `JOIN_LOYALTY` only when joining can succeed.

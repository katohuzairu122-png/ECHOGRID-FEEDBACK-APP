**Status: DESIGN PROPOSAL — DOCUMENTATION ONLY. No code, schema, endpoint or configuration is created or changed.**

## 1. Binding principles

1. **Fail closed.** Any missing, stale, ambiguous or inconsistent publication fact means "not discoverable".
2. **Discovery is not consent.** Viewing a profile, Community membership, loyalty membership, an OTP login, a survey
   response and a transactional-notification default are **never** advertising consent (BDPN v1.0 section 3).
3. **Tenant isolation is unchanged.** No profile read or write path may expose, count, rank by, or infer another
   business's customers, loyalty configuration or private data.
4. **Platform decides publication; business decides content.** No business-side code path can publish.
5. **Immutable evidence.** What a moderator approved is exactly what is shown, proven by a content digest.
6. **No synthetic data.** No rating, reach, popularity, proximity, opening status, offer or outcome is displayed
   unless it is real, verified, and separately authorized.
7. **Least data.** The public contract exposes the minimum approved fields; internal ids and operational data stay internal.

## 2. Permission matrix (proposed)

Permission **keys are proposals** (D-02, D-03). Business permissions would join the existing business-scoped role
catalog; moderation would follow the existing **code-owned platform permission** pattern layered on
`requirePlatformRole` (see `platform/community-permissions.ts`), re-resolved from the database on every request.

| Actor                                                                               | View own draft/state                                                 | Edit draft                              | Submit | Withdraw / re-publish | Approve / reject                     | Suspend / lift | Read public discovery            |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------- | ------ | --------------------- | ------------------------------------ | -------------- | -------------------------------- |
| **Profile owner / business admin** (business-wide `profile:edit`, `profile:submit`) | Yes (own business only)                                              | Yes                                     | Yes    | Yes                   | **No**                               | **No**         | Yes only as a customer           |
| **Business staff without the permission**                                           | No                                                                   | No                                      | No     | No                    | No                                   | No             | n/a                              |
| **Branch-scoped business user**                                                     | No (profile is business-wide, mirroring `requireBusinessWideAccess`) | No                                      | No     | No                    | No                                   | No             | n/a                              |
| **Platform moderator** (`profile:moderate`, role set decided in D-03)               | Any profile (review queue)                                           | **No** (cannot author business content) | No     | No                    | Yes (not own submissions; see below) | Yes            | n/a                              |
| **Platform support** (read only, if granted in D-03)                                | Read-only                                                            | No                                      | No     | No                    | No                                   | No             | n/a                              |
| **Impersonating session** (platform admin as business user)                         | Read-only                                                            | **No**                                  | **No** | **No**                | **No**                               | **No**         | n/a                              |
| **Ordinary customer** (active, authenticated)                                       | n/a                                                                  | No                                      | No     | No                    | No                                   | No             | **Yes**, published profiles only |
| **Suspended/inactive customer**                                                     | n/a                                                                  | No                                      | No     | No                    | No                                   | No             | No (forbidden state)             |
| **Anonymous visitor**                                                               | n/a                                                                  | No                                      | No     | No                    | No                                   | No             | **No in v1** (D-09)              |

Additional rules:

- **Separation of duties:** the approver must be a different user from the submitter; a business user can never
  hold moderation authority through a business role.
- **Impersonation cannot author, submit, withdraw or moderate**, mirroring the existing rule that impersonation
  cannot accept Partner terms (`PARTNER_CONSENT_IMPERSONATION_DENIED`).
- **Authorization is re-resolved from the database** on every request, never trusted from the token.
- **What a moderator may see of private business data during review** is limited to the minimum needed and is an owner decision (D-22).
- **Whether a two-person rule applies to suspension** and which platform roles may moderate are owner decisions (D-03).

## 4. Threat model

| #    | Threat                                           | Vector                                                                                     | Required control (proposed)                                                                                                                                                                                                                                                                               | How it is verified (BDPN-01E)                                                                                                            |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| T-01 | **Cross-tenant business data exposure**          | A read joins to private tables; a DTO accidentally carries an internal field               | Discovery reads only the live **approved revision** tables and the platform category catalog; a closed DTO allow-list; no join to customers, loyalty, memberships, branches' coordinates or billing                                                                                                       | Contract test asserts the exact DTO key set; query-plan review; adversarial test with a business that has private data                   |
| T-02 | **Unauthorized publication**                     | A business sets state or pointer directly; mass-assignment; direct SQL by the app role     | State changes only through the transition service; DB `CHECK` and composite FK prevent a pointer to a non-approved or foreign revision; the application role has no `UPDATE` on `published_revision_id`/`publication_state` except through the audited path                                               | DB negative tests (as in the Gate 2 non-owner suites); API tests for every illegal transition                                            |
| T-03 | **Unapproved profile update goes live**          | Editing a revision after approval; editing the live row in place                           | Revisions are immutable once `submitted` (DB guard); the live pointer moves only on approval; edits create a new revision                                                                                                                                                                                 | Test: mutate approved revision, expect rejection; test: edit while live, expect old content still served                                 |
| T-04 | **Approve-then-edit race (TOCTOU)**              | Business edits between a moderator opening and approving                                   | Approval names the exact revision id **and content digest**; a mismatch aborts; submitted content is frozen                                                                                                                                                                                               | Concurrency test with interleaved edit and approve                                                                                       |
| T-05 | **Leaking private contact data**                 | Reusing user email/phone or owner details as "contact"                                     | Public contact is **separate, explicitly entered and separately approved** fields; never derived from `users`, `customers`, `branches` or billing                                                                                                                                                         | Test: profile with no public contact returns null contact even when the owner has an email and phone                                     |
| T-06 | **Customer identity exposure**                   | Reports, view counts, "customers also joined", per-customer logs                           | No per-customer view history in v1 (D-17); no customer data in any discovery DTO; business-visible reporting, if ever added, is aggregate and privacy-thresholded per BDPN v1.0                                                                                                                           | Contract test; log review that discovery requests do not persist customer-identifying analytics                                          |
| T-07 | **Unapproved advertising / promotion**           | Using discovery as a back door to send or boost                                            | No notification, event type, consent grant or send path is introduced; no sponsored flag or ranking input exists; no outbound channel                                                                                                                                                                     | Static scan for new notification event types; test that no `notifications` or `consent_grants` rows are created by any discovery request |
| T-08 | **Search and enumeration abuse**                 | Scraping all profiles; probing ids; wildcard searches                                      | Authenticated customers only (D-09); opaque handles distinct from `businesses.id` (D-10); keyset pagination with a hard page-size cap; **no total count**; search minimum length, maximum length and escaped wildcards; per-customer rate limit; uniform not-found for unknown **and** ineligible handles | Rate-limit and uniform-response tests; test that unknown, unpublished, suspended and withdrawn handles are indistinguishable             |
| T-09 | **Publication-status race conditions**           | Concurrent submit/approve/withdraw/suspend                                                 | One transaction per transition; row lock on the publication record (`FOR UPDATE`) or version check; a partial unique index of one `submitted` revision per business; idempotency keys on business writes                                                                                                  | Concurrency tests like the repository's existing PG18 concurrency proofs                                                                 |
| T-10 | **Cache disclosure after unpublishing**          | Shared or browser caching of a withdrawn profile or image                                  | `private, no-store` on all discovery responses; no shared-cache of customer-session responses; media only via short-lived signed URLs; optional epoch-tagged caching only if D-12 approves it                                                                                                             | Header tests; test that a withdrawn profile is unreachable on the very next request; signed-URL expiry test                              |
| T-11 | **Stored XSS / content injection**               | Rich text, markdown or HTML in names and descriptions; `javascript:` URLs                  | Plain-text only; output escaped by the framework; URL fields `https` only; no HTML rendering of profile text; control and bidi-override characters rejected or normalized                                                                                                                                 | Fuzz/negative tests on every text and URL field                                                                                          |
| T-12 | **Malicious or illegal media**                   | Upload of executable or disguised files, huge images, tracking pixels, EXIF location leaks | Dedicated upload design (D-05): content-type allow-list verified by sniffing, size and dimension caps, server-side re-encode, metadata stripping, no remote image URLs, object keys namespaced per business, serving via signed URLs                                                                      | Separate threat review before any media is accepted                                                                                      |
| T-13 | **Moderator abuse or error**                     | A moderator approves their own business, or approves unseen content                        | Separation of duties; approval records reviewer, digest and reason; every decision audited; platform audit log readable by `support                                                                                                                                                                       | billing                                                                                                                                  | admin` | Test: self-approval refused; audit row exists for every transition |
| T-14 | **Impersonation abuse**                          | A platform admin acting as a business to publish or approve                                | Impersonation sessions are denied all profile writes and moderation                                                                                                                                                                                                                                       | Test with an impersonation token on every write route                                                                                    |
| T-15 | **Derived-state drift**                          | A cached "is public" flag disagrees with reality                                           | No denormalized public flag; the eligibility predicate is evaluated by the query (spec 3.4)                                                                                                                                                                                                               | Test that changing `businesses.status` to suspended hides the profile on the next read with no profile-table change                      |
| T-16 | **Unsafe reuse of the existing public endpoint** | Treating `GET /businesses/:id/public` as proof of publication                              | Documented as not publication-gated (section 3); discovery uses its own endpoints and read model                                                                                                                                                                                                          | Review checkpoint in BDPN-01C; test that an unpublished business is absent from discovery although `/public` resolves                    |
| T-17 | **Personalization creep**                        | Ranking or filtering by customer history                                                   | The query takes no customer identifier input; ordering is `display_name`, then handle; a test asserts two different customers receive identical results                                                                                                                                                   | Equality test across customers with different histories                                                                                  |
| T-18 | **Moderation queue disclosure**                  | Business or customer reads other businesses' pending content                               | Pending and rejected revisions are readable only by the owning business and platform moderators; never by customers or other businesses                                                                                                                                                                   | Authorization tests per role                                                                                                             |
| T-19 | **Denial of service via expensive search**       | Pathological search strings or deep pagination                                             | Bounded query length, indexed prefix/trigram strategy decided in BDPN-01C, keyset pagination only, statement timeout                                                                                                                                                                                      | Load/negative tests in disposable PostgreSQL                                                                                             |
| T-20 | **Language/locale confusion**                    | Serving text from the wrong locale or leaking draft translations                           | Locale resolution is per field with an explicit `contentLocale`; only translations of the **approved** revision are readable                                                                                                                                                                              | Tests with partial translations                                                                                                          |

## 5. Consent boundaries (explicit)

| Statement                                           | Rule                                                                                                                                                                                                                 |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Customer opens the discovery module                 | Creates nothing. No membership, no loyalty account, no consent grant, no notification, no points.                                                                                                                    |
| Customer is a Community member                      | Gives **no** advertising permission and is **not required** to browse.                                                                                                                                               |
| Customer has a loyalty relationship with business A | Gives business B **no** access to that relationship and no right to contact the customer.                                                                                                                            |
| Business publishes a profile                        | Does **not** authorize any contact with customers; it only makes approved public information viewable inside Echo Grid.                                                                                              |
| Future promotion (BDPN-02 and later)                | Requires its own platform-level, channel-specific, versioned, revocable consent contract and security review, and is **not** designed or enabled here.                                                               |
| `consent_grants.marketing`                          | Not created, read, interpreted or modified by BDPN-01. Its present storage shape does not establish valid platform-wide marketing consent.                                                                           |
| Contact details on a profile                        | Are business-published public information shown to authenticated customers; they are not a customer-to-business contact channel created by Echo Grid and **never** include any customer data in the other direction. |

## 6. Audit evidence and failure behavior

Proposed `audit_log` actions (namespaced, with the exact revision id and content digest in `metadata`):
`business_profile.draft_saved`, `.submitted`, `.approved`, `.rejected`, `.published`, `.updated`, `.withdrawn`,
`.republished`, `.suspended`, `.suspension_lifted`. Each records actor, business, entity id, timestamp and reason
code. Review free-text notes stay internal and are never exposed to customers.

Failure behavior:

- Transition and audit write are one transaction; failure of either rolls back both.
- A read that finds an inconsistent record **omits it** and raises an operator-visible log entry; it never shows
  partial or unapproved content.
- A suspension takes effect on the next request (no TTL grace for text; media signed-URL lifetime is the only tail, D-12).
- If the moderation service or its database path is unavailable, **nothing is auto-approved**; submissions queue.
- If discovery is administratively disabled (D-20), endpoints respond with a uniform "not available" and the Community
  Hub entry card is hidden.

## 7. Verification requirements (for BDPN-01E)

1. Contract tests that assert the **exact** key set of every discovery DTO and fail on any added field.
2. Authorization tests for every actor in section 2 against every route.
3. State-machine tests: every legal transition passes; every illegal transition is rejected, including cross-business
   pointer attempts and self-approval.
4. Concurrency tests on disposable PostgreSQL 18 following the existing Gate 2 patterns.
5. Tenant isolation: non-owner role, forced RLS and denial tests extended to the new tables, consistent with the
   existing Gate 2 suites.
6. Negative tests for T-05, T-06, T-07, T-10, T-15, T-16 and T-17 exactly as written above.
7. A static check that no new notification event type, channel or `consent_grants` write is introduced.
8. A migration replay test from the current head and the Gate 2 re-pin check (sequence document).
